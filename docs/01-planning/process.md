# Обоснование процесса и настройка рабочего потока команды

**Цель:** Выбрать и обосновать методологию разработки, настроить таск-трекер с визуализацией потока задач, рассчитать и обосновать лимиты незавершенной работы (WIP) на основе закона Литтла, а также зафиксировать критерии готовности задач (DoR/DoD).

---

## 1. Выбор методологии управления разработкой

Для реализации нашего командного проекта была выбрана методология **Scrumban**. Данный выбор обоснован следующими факторами:

* **Гибридный подход:** От Scrum мы берем фиксированные временные рамки (итерации в 1 неделю) для регулярного планирования, синхронизации и взаимной проверки артефактов (код-ревью). От Kanban — фокус на непрерывном визуализированном потоке задач и жесткое ограничение объема незавершенной работы (WIP-лимиты) для устранения узких мест.
* **Неопределенность на старте:** Проект находится на этапе проектирования MVP, где требования могут уточняться. Scrumban позволяет не перегружать команду жесткими спринтами, а оперативно вытягивать наиболее приоритетные задачи из бэклога по мере освобождения ресурсов.
* **Ограниченный размер команды:** Так как в команде всего 2 человека, классический Scrum с его строгими ролями (Scrum-мастер, Product Owner) избыточен. Scrumban позволяет сфокусироваться на оптимизации индивидуальной пропускной способности.

## 2. Настройка доски задач и обоснование WIP-лимитов

Рабочее пространство организовано в GitHub Projects. Доска разделена на 5 колонок, отражающих реальный жизненный цикл задачи в нашем проекте:

1. **Бэклог (Backlog):** Общий упорядоченный список пользовательских историй (User Stories). Лимит отсутствует.
2. **Готово к работе (Ready for Dev):** Задачи, успешно прошедшие фильтр DoR и готовые к выполнению.
3. **В работе (In Progress):** Задачи, которые находятся в стадии активной реализации (написание кода, скриптов, документации). **WIP-лимит = 2**.
4. **Ревью (Review / Pull Request):** Задачи, оформленные в виде Pull Request на GitHub и ожидающие проверки вторым участником команды. **WIP-лимит = 1**.
5. **Готово (Done):** Задачи, полностью завершенные согласно критериям DoD. Лимит отсутствует.

### Математическое обоснование WIP-лимитов по закону Литтла
Согласно **закону Литтла**, среднее время цикла ($CT$ — Cycle Time) напрямую зависит от объема незавершенной работы ($WIP$ — Work in Progress) и средней пропускной способности системы ($Th$ — Throughput):

$$CT = \frac{WIP}{Th}$$

* **Для этапа «В работе» (In Progress):** Учитывая, что в команде 2 разработчика (Андрей и Даниил), выделение лимита **WIP = 2** гарантирует, что в один момент времени каждый участник сфокусирован строго на *одной* задаче. Это исключает потери времени на контекстное переключение (context switching). Если один из участников застревает, лимит заставит напарника подключиться к решению проблемы (пассивное парное проектирование), а не брать новую задачу.
* **Для этапа «Ревью» (Review):** Установлен жесткий лимит **WIP = 1**. Это сделано для того, чтобы этап проверки не становился бутылочным горлышком (узким местом). Как только в колонке «Ревью» появляется задача, второй участник обязан переключиться на код-ревью перед тем, как брать следующую задачу из бэклога. Это искусственно снижает время цикла ($CT$) для готовых фич и ускоряет поставку ценности.

## 3. Критерии Definition of Ready (DoR) и Definition of Done (DoD)

Для минимизации брака на входе в разработку и стандартизации качества на выходе установлены следующие соглашения:

### Definition of Ready (DoR) — Готовность к началу работы
Задача может быть переведена из колонки «Бэклог» в колонку «Готово к работе» только если она удовлетворяет критериям **INVEST**:
* **I**ndependent — Задача независима от других или ее зависимости явно зафиксированы.
* **N**egotiable — Суть задачи понятна обоим участникам, детали реализации могут обсуждаться.
* **V**aluable — Задача несет явную ценность для пользователя или архитектуры MVP.
* **E**stimable — Задача оценена на сессии Planning Poker в Story Points (зафиксировано в `estimates.md`).
* **S**mall — Задача декомпозирована так, что ее можно выполнить за 2-3 дня.
* **T**estable — Сформулированы как минимум **два критерия приемки** в строгом текстовом формате **Дано / Когда / Тогда**.

### Definition of Done (DoD) — Критерии полной готовности
Задача считается полностью завершенной и перемещается в колонку «Готово» только при выполнении всех следующих условий:
1. **Функциональность:** Код полностью реализует сценарий пользовательской истории и проходит все критерии приемки (Acceptance Criteria).
2. **Качество кода:** Код не содержит явных синтаксических ошибок, мусорных комментариев и отформатирован по стандарту PEP8 (для Python-скриптов).
3. **Автоматизация (CI):** Создан Pull Request в ветку `main`, автоматические тесты и проверки на GitHub Actions (если настроены) успешно пройдены («зеленый CI»).
4. **Код-ревью:** Получено явное одобрение (Approve) от второго участника команды в интерфейсе GitHub.
5. **Документирование:** Все сопутствующие расчеты, графики, CSV-файлы и Markdown-документы обновлены в папке `docs/` и воспроизводимы.

## Выводы по этапу
Выбранный процесс в формате Scrumban сбалансирован под команду из двух человек. Использование закона Литтла для ограничения WIP позволяет максимизировать фокус и скорость доставки MVP. Четкие границы DoR/DoD страхуют команду от размытия рамок проекта (scope creep) и гарантируют высокое качество артефактов, отправляемых на проверку преподавателю.
