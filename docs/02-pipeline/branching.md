# Стратегия ветвления и правила разработки (`branching.md`)

**Проект:** Автоматизированный таск-трекер «OptiPlan»  
**Этап:** Лабораторная работа № 2 — Инженерный конвейер: Git-процесс, ревью и непрерывная интеграция  
**Авторы:** Сухарев Андрей (Участник А), Даниил Антонюк (Участник Б)

---

## 1. Цель документа
Формализовать единый процесс работы с системой контроля версий Git, правила именования веток, регламент оформления коммитов и процедуру проведения код-ревью (Pull Request) для обеспечения стабильности основной ветки и минимизации времени цикла (Cycle Time) задач при разработке MVP «OptiPlan».

---

## 2. Выбор и обоснование стратегии ветвления

Для командной разработки проекта выбран подход **GitHub Flow**.

### Обоснование выбора:
1. **Размер команды и темп работы:** В проекте участвуют 2 разработчика (Андрей и Даниил). Сложные модели с долгоживущими ветками (например, *Git Flow* с ветками `develop`, `release/*`, `hotfix/*`) создают избыточные накладные расходы на слияние и разрешение конфликтов.
2. **Непрерывная интеграция и доставка:** Ветка `main` всегда находится в рабочем, протестированном состоянии, готовом к развёртыванию.
3. **Согласованность с WIP-лимитами:** Короткоживущие тематические ветки напрямую поддерживают установленные на Этапе 1 ограничения незавершённой работы (Scrumban) и предотвращают накопление неинтегрированного кода.

### Схема работы по GitHub Flow:
```text
main       ●───────────●───────────────────●───────────●──▶ (всегда стабильна)
            \         /                     \         /
feat/auth    ●───●───● (PR #1 + CI + Review) \       /
                                              \     /
feat/tasks                                     ●───● (PR #2 + CI + Review)
```

## 3. Правила работы с ветками

### 3.1. Основная ветка (`main`)
* Является единственной постоянной веткой в репозитории.
* Прямые коммиты (`git push origin main`) строго запрещены настройками защиты ветки (Branch Protection Rules).
* Любые изменения попадают в `main` исключительно через одобренный Pull Request после успешного прохождения проверок CI.

### 3.2. Соглашение об именовании рабочих веток
Все рабочие ветки ответвляются от актуального состояния `main` и именуются в нижнем регистре с использованием дефисов (`kebab-case`) по шаблону:

`<тип>/<номер-задачи>-<краткое-описание>` (либо `<тип>/<краткое-описание>`, если задача не привязана к Issue).

| Префикс (тип) | Назначение ветки | Пример |
| :--- | :--- | :--- |
| `feat/` | Реализация новой функциональности или истории MVP | `feat/12-task-creation-api` |
| `fix/` | Исправление ошибок и багов | `fix/18-db-connection-timeout` |
| `ci/` | Настройка и оптимизация конвейера CI/CD, Docker | `ci/setup-github-actions` |
| `docs/` | Написание и обновление проектной документации | `docs/branching-strategy` |
| `refactor/` | Рефакторинг кода без изменения внешнего поведения | `refactor/healthcheck-module` |
| `test/` | Добавление или исправление модульных тестов | `test/user-service-coverage` |

### 3.3. Время жизни веток
* **Рекомендуемое время жизни:** 1–2 рабочих дня (не более 3 дней).
* После успешного слияния Pull Request в `main` рабочая ветка **подлежит немедленному удалению** (настроено автоматическое удаление веток после merge в настройках GitHub).

## 4. Соглашение о сообщениях коммитов (Conventional Commits)

Для поддержания читаемой истории изменений и автоматизации версионирования команда использует спецификацию **Conventional Commits 1.0.0**.

### Формат сообщения:
```text
<тип>(<область>): <краткое описание в повелительном наклонении>

[необязательное тело коммита]
```

### Допустимые типы коммитов:
* `feat:` — добавление новой функциональности (истории MVP);
* `fix:` — исправление бага;
* `ci:` — изменения в файлах конвейера (`.github/workflows/*`) или Docker;
* `docs:` — изменения исключительно в документации (`docs/`, `README.md`);
* `style:` — форматирование кода, исправление отступов (без изменения логики);
* `refactor:` — рефакторинг продакшн-кода;
* `test:` — добавление или обновление тестов;
* `chore:` — обновление зависимостей, настройка линтеров, шаблонов.

### Примеры корректных коммитов:
* `feat(api): add endpoint for creating new task`
* `fix(db): handle connection pool exhaustion on startup`
* `ci(actions): add dependency caching for pip`
* `docs(pipeline): describe branching strategy and PR rules`

## 5. Правила слияния и процесс Code Review

### 5.1. Требования к Pull Request (PR)
1. **Атомарность:** Один Pull Request решает строго одну задачу или пользовательскую историю MVP.
2. **Ограничение объёма:** Размер одного PR не должен превышать **400 изменённых строк кода** (без учёта lock-файлов и автоматически сгенерированных артефактов). Если задача превышает лимит, она декомпозируется на несколько последовательных PR.
3. **Связь с бэклогом:** В описании PR обязательно указывается ссылка на связанную задачу на доске проекта с помощью ключевых слов (`Closes #<id>` или `Refs #<id>`).
4. **Заполнение шаблона:** При создании PR автор заполняет стандартный чек-лист из `.github/PULL_REQUEST_TEMPLATE.md`.

### 5.2. Регламент ревью и матрица ответственности
* **Взаимное ревью:** Каждый PR, созданный Участником А (Сухарев Андрей), проверяет Участник Б (Даниил Антонюк), и наоборот. Назначение ревьюеров происходит автоматически через файл `.github/CODEOWNERS`.
* **SLA на проверку:** Рецензент обязуется провести первичное ревью в течение **24 часов** с момента перевода PR из статуса *Draft* в *Ready for review*.
* **Качество обратной связи:** Ревью должно содержать минимум **один содержательный комментарий** (по архитектуре, читаемости, обработке граничных случаев, тестам или производительности) либо аргументированное замечание. Формальные апрувы без просмотра кода не допускаются.
* **Реакция автора:** Автор вносит исправления по замечаниям и отвечает на комментарии в течение **24 часов**.

### 5.3. Технические условия слияния (Branch Protection Rules)
В настройках репозитория GitHub для ветки `main` активированы следующие правила защиты:
* **Require a pull request before merging** — включено;
* **Require approvals** — минимум `1` одобрение (Approve) от партнёра по команде;
* **Dismiss stale pull request approvals when new commits are pushed** — включено (сброс апрува при добавлении новых коммитов после ревью);
* **Require status checks to pass before merging** — включено (обязательный зелёный статус всех джобов CI-конвейера: линтер, тесты, сборка Docker-образа);
* **Метод слияния:** используется **Squash and merge** (для объединения промежуточных рабочих коммитов ветки в один чистый коммит по стандарту Conventional Commits в ветке `main`).
